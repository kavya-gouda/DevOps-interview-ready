### SEC-001 | Signing Every Container Image in CI
**Type:** Implement | **Difficulty:** Hard | ⬜

> You're asked to enforce image signing so that only signed images can run in production Kubernetes clusters. Walk through the full implementation.

**What you must cover:**
- Cosign + Sigstore: keyless signing using OIDC identity from GitHub Actions
- `cosign sign` step in CI pipeline, attaching signature to OCI registry
- Verifying signatures at admission: Kyverno `ClusterPolicy` with `verifyImages` block
- Policy enforcement: `verify` vs `audit` mode during rollout
- What happens if an unsigned image is deployed directly via `kubectl apply`

**Key commands:**
```bash
# Sign in CI (keyless with OIDC)
cosign sign --yes $ACR_LOGIN_SERVER/$IMAGE_NAME@$DIGEST

# Kyverno verify policy
kubectl apply -f - <<EOF
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signature
spec:
  validationFailureAction: Enforce
  rules:
  - name: verify-cosign
    match:
      resources:
        kinds: ["Pod"]
    verifyImages:
    - imageReferences: ["myacr.azurecr.io/*"]
      attestors:
      - entries:
        - keyless:
            subject: "https://github.com/myorg/*"
            issuer: "https://token.actions.githubusercontent.com"
EOF
```

### SEC-011 | Container Image Hardening Checklist
**Type:** Explain | **Difficulty:** Medium | ⬜

- Trivy scan: must pass with no Critical fixable vulns before push

### SEC-025 | Zero Secrets at Container Runtime

### SEC-031 | Falco — Writing Custom Rules
**Type:** Implement | **Difficulty:** Hard | ⬜

> Write a Falco rule to detect when a container tries to read `/etc/shadow` or spawn a shell inside a production pod.

**What you must cover:**
```yaml
- rule: Shell Spawned in Production Container
  desc: A shell was spawned in a container — possible intrusion or debug access
  condition: >
    spawned_process and
    container and
    (proc.name in (shell_binaries)) and
    not proc.pname in (allowed_parent_processes)
  output: >
    Shell spawned (user=%user.name user_loginuid=%user.loginuid
    pod=%k8s.pod.name ns=%k8s.ns.name cmd=%proc.cmdline)
  priority: WARNING
  tags: [container, shell]

- rule: Read Sensitive File in Container
  desc: Attempt to read /etc/shadow inside a container
  condition: >
    open_read and container and
    fd.name in (/etc/shadow, /etc/sudoers, /root/.ssh/authorized_keys)
  output: "Sensitive file read (pod=%k8s.pod.name file=%fd.name user=%user.name)"
  priority: ERROR
  tags: [container, filesystem]
```
- Rule logic: `spawned_process`, `container`, macro expansion
- Output fields: `%k8s.pod.name`, `%k8s.ns.name`, `%proc.cmdline`
- Deployment: DaemonSet on all nodes, privileged, host PID namespace
- Alerting: Falco sidekick → Slack / PagerDuty

### SEC-033 | Container Escape Scenarios
**Type:** Explain | **Difficulty:** Expert | ⬜

> Name 3 real container escape techniques and explain how each one is mitigated.

**What you must cover:**
- **Privileged container + host mount**: `--privileged` with `/` mounted gives full host access → prevent with PSS `Restricted`, ban `privileged: true`
- **runc vulnerability (CVE-2019-5736)**: writing to `/proc/self/exe` while runc is executing → fixed in runc, keep runtime patched, monitor CVEs on runtime
- **Dirty Pipe (CVE-2022-0847)**: kernel vuln allowing overwrite of read-only files → kernel patch; Falco rule detects exploit attempt
- **hostPID + kill/ptrace**: `hostPID: true` lets container ptrace host processes → ban `hostPID`, `hostNetwork`, `hostIPC` in PSS
- **Mounted Docker socket**: `docker.sock` inside container = root on host → ban mounting `docker.sock` via Kyverno policy
